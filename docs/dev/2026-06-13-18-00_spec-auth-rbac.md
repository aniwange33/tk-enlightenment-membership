## Overview

The membership application currently has **no authentication or authorization** — every REST endpoint is open, there is no Admin vs Member distinction, and the temporary password generated for the welcome email is thrown away (no credentials are ever persisted).

This step introduces a dedicated **`auth` module** that owns identity: persisted accounts, login via **stateless JWT**, role-based access control (Admin vs Member), enforced first-login password change, and synchronisation of account login-ability with member status. It closes **US-1, US-9, US-10** from the domain spec and establishes the access-control foundation every other journey assumes.

**Out of scope for this step (deferred):** password reset / forgot-password (US-14), admin announcements (US-7), and any web/UI frontend.

## Decisions (from interview)

| # | Decision | Choice |
|---|----------|--------|
| 1 | Auth mechanism | **Stateless JWT** (signature-only validation, no server session) |
| 2 | Where identity lives | **New `auth` module** (owns credentials, roles, account lifecycle) |
| 3 | Step scope | **Login + RBAC + forced first-login password change** |
| 4 | First admin | **Seeded** via Flyway migration / startup seeder, credentials from `.env` |
| 5 | Revocation model | **Pure stateless, short TTL** — no per-request DB check; revocation lag = token TTL |
| 6 | Temp-password flow | **Auth emits `AccountCreatedEvent`**; notification welcome email listens to it |
| 7 | Member self-access | **Both** — `/api/me*` convenience endpoints **and** owner-or-admin checks on `/api/members/{id}/**` |
| 8 | Forced password change | **Block all endpoints except change-password** until completed |
| 9 | Who may log in | **Only ACTIVE members** (plus all Admins); INACTIVE/SUSPENDED/TERMINATED members cannot log in |
| 10 | Access token TTL | **8 hours**, configurable via `.env` |

**Defaulted (not separately asked):** BCrypt password hashing; HMAC-SHA256 (HS256) JWT signed with a secret from `.env` (same pattern as mail credentials); minimum password length 8; logout is client-side (token discard), no server logout endpoint.

## Roles

| Role | Source | Login allowed when | Notes |
|------|--------|--------------------|-------|
| **ADMIN** | Seeded (first admin) or created by an existing Admin (future) | Always (account `enabled`) | Equal privileges across all admins. Not tied to a member record. |
| **MEMBER** | Auto-created when a member is registered | Member status is **ACTIVE** only | Linked 1:1 to a `memberId`. |

One role per account (no multi-role). Email is the unique login identifier across **all** accounts.

**Dependency flow (no cycles):**
- `auth` → `member` via `MemberAPI` (read member status/details when needed) — one-way.
- `member` → `auth`: **events only** (`auth` listens to `MemberRegisteredEvent`, `MemberStatusChangedEvent`).
- `auth` → `notification`: **events only** (`auth` publishes `AccountCreatedEvent`; notification listens).
- `auth` → `shared` (OPEN).

## Account Lifecycle & Event Flow

The member events already carry everything needed (`memberId`, `email`, `fullName`, `membershipNumber`, `newStatus`) — **no change to member-module event payloads is required.**

1. **Member registered** → `MemberRegisteredEvent` →
   `auth` creates a `UserAccount` (role `MEMBER`, `enabled=true` since new members are ACTIVE, `mustChangePassword=true`), generates a temporary password, BCrypt-hashes it, and publishes
   **`AccountCreatedEvent(email, fullName, membershipNumber, tempPassword)`**.
2. **Welcome email** → notification's welcome handler **switches from `MemberRegisteredEvent` to `AccountCreatedEvent`** so it sends the *real* temp password. (Remove the throwaway password generator in `MemberEventNotificationListener`.)
3. **Member status changed** → `MemberStatusChangedEvent` →
   `auth` sets `enabled = (newStatus == ACTIVE)`. So auto-inactivation (May 1), suspension, and termination all revoke login; marking dues paid (INACTIVE → ACTIVE) restores it.
4. **Member re-registered after TERMINATED** → new `MemberRegisteredEvent` → new account created (old account remains disabled). Email uniqueness must be reconciled — see Edge Cases.

> **Revocation lag:** because tokens are validated by signature only (no per-request DB lookup), a member disabled mid-session keeps access until their current token expires (≤ 8h). Accepted per Decision 5/10.

## JWT Design

- **Algorithm:** HS256, secret from `AUTH_JWT_SECRET` (`.env`; add to `.env.example`).
- **TTL:** `AUTH_JWT_TTL` (default **8h**).
- **Claims:** `sub` = account id, `email`, `role`, `memberId` (nullable), `mustChangePassword` (bool), `exp`, `iat`.
- **Validation:** `JwtAuthenticationFilter` validates signature + expiry, builds the `Authentication` from claims. No DB read.
- **Stateless:** `SessionCreationPolicy.STATELESS`, CSRF disabled (no cookies; bearer token in `Authorization` header).
- **Logout:** client discards the token (no server endpoint).

## Endpoints

### Auth (public / semi-public)
| Method | Path | Access | Behaviour |
|--------|------|--------|-----------|
| POST | `/api/auth/login` | Public | `{email, password}` → `200 {token, mustChangePassword}`; `401` on bad credentials; `403`/`401` if account disabled (non-ACTIVE member or TERMINATED) |
| POST | `/api/auth/change-password` | Any authenticated (incl. `mustChangePassword`) | `{currentPassword, newPassword}` → validates current, sets new hash, clears `mustChangePassword`, **returns a fresh token** without the flag |

### Self-service (`MEMBER` with a linked member; also usable by any authenticated member)
| Method | Path | Access |
|--------|------|--------|
| GET | `/api/me` | Authenticated; resolves member from token `memberId` (`404`/`409` if no linked member, e.g. an admin) |
| PUT | `/api/me` | Authenticated; update own `phone`, `address` only |
| GET | `/api/me/dues` | Authenticated; own dues history |

### Existing member/dues routes — now secured
| Method | Path | Access |
|--------|------|--------|
| POST | `/api/members` | **ADMIN** |
| GET | `/api/members` | **ADMIN** |
| GET | `/api/members/{id}` | **ADMIN or owner** |
| PATCH | `/api/members/{id}/status` | **ADMIN** |
| PUT | `/api/members/{id}/profile` | **ADMIN or owner** |
| POST | `/api/members/{id}/dues/{year}/pay` | **ADMIN** (members cannot pay their own dues — US-13 read-only) |
| GET | `/api/members/{id}/dues` | **ADMIN or owner** |

### Unauthenticated allow-list
`/api/auth/login`, `/swagger-ui/**`, `/v3/api-docs/**`, error dispatch. Everything else requires authentication.

### Forced password change gate
While the token's `mustChangePassword=true`, a filter/handler rejects **every** request except `POST /api/auth/change-password` with **403** (`{detail: "Password change required"}`).

## First Admin Seeding

- Startup seeder (or `V5__seed_admin.sql` + config) inserts **one** ADMIN account if none exists.
- Credentials from `.env`: `AUTH_ADMIN_EMAIL`, `AUTH_ADMIN_PASSWORD` (add both to `.env` and `.env.example`).
- Seeded admin has `mustChangePassword=true`, `enabled=true`, `memberId=null`.
- Idempotent: skip if an ADMIN already exists.

## Cross-Cutting Invariants

- **No cross-module service calls** except via `*API` facades; `member` → `auth`/`notification` only through events. `ApplicationModules.verify()` must stay green.
- **Visibility:** `UserAccountEntity`, repository, services, JWT classes are **package-protected**; only `AuthAPI`, DTOs, `Role`, and `AccountCreatedEvent` are public.
- **Every state-changing endpoint is authorised** — default-deny: any route not in the allow-list requires authentication, and member/dues mutations require ADMIN unless explicitly owner-allowed.
- **Passwords never logged or returned** — only the one-time temp password leaves the system, via the welcome email.
- **Email uniqueness** holds across all accounts (mirrors member email uniqueness).
- Secrets (`AUTH_JWT_SECRET`, `AUTH_ADMIN_PASSWORD`) live in `.env`, never committed.

## Edge Cases & Constraints

- **Bad login:** generic `401` (do not reveal whether email exists).
- **Disabled account login** (INACTIVE/SUSPENDED/TERMINATED member): login refused even with correct password.
- **INACTIVE member locked out:** consequence of Decision 9 — an unpaid member cannot log in to view their own dues until an admin marks them paid (status → ACTIVE → account re-enabled). Documented and accepted.
- **`mustChangePassword` token still flagged after change:** the change-password endpoint issues a new token; the old one keeps the flag until expiry but only permits change-password, so no lockout.
- **`/api/me` for an admin** (no linked member): `409 Conflict` / `404` — admins use `/api/members`.
- **Re-registration after TERMINATED:** new member ⇒ new account; the old disabled account still owns the email. Resolution: on `MemberRegisteredEvent`, if an account with that email exists and is **disabled**, repoint it to the new `memberId`, reset password (new temp), `enabled=true`, `mustChangePassword=true`; otherwise reject duplicate. (Confirm during implementation.)
- **Admin self-termination:** if a future admin is also linked to a member, block terminating one's own linked member; otherwise N/A (admins aren't members).
- **Clock:** token expiry uses the shared `Clock` bean for testability.
- **Concurrency:** account creation from the registration event must be idempotent (unique email) to tolerate event redelivery (Modulith republish-on-restart is enabled).

## User Journeys

### Journey A: Member First Login & Forced Password Change
1. Member receives welcome email (real temp password) → calls `POST /api/auth/login` with email + temp password.
2. Response includes `mustChangePassword=true`; all other endpoints return `403` until changed.
3. Member calls `POST /api/auth/change-password` → receives a fresh token without the flag.
4. Member now calls `/api/me`, `/api/me/dues`, etc.

### Journey B: Admin First Login
1. Seeded admin logs in with `.env` credentials; `mustChangePassword=true`.
2. Changes password → full ADMIN access to `/api/members/**`.

### Journey C: Member Self-Service
1. Authenticated member calls `GET /api/me` (profile) and `GET /api/me/dues` (history).
2. Updates contact details via `PUT /api/me` (phone, address only).

### Journey D: Status-Driven Access Changes
1. May 1 job inactivates an unpaid member → `MemberStatusChangedEvent` → account disabled.
2. Member can no longer log in (existing token works until ≤8h expiry).
3. Admin marks dues paid → member ACTIVE → account re-enabled → member can log in again.

## User Stories

- **US-A1**: As an unauthenticated user, I POST credentials to `/api/auth/login` and receive a JWT so that I can access protected endpoints. *(entry point)*
- **US-A2**: As an Admin, I log in with seeded credentials so that I can reach the member-management endpoints. *(entry point)*
- **US-A3**: As a Member, I log in with the temporary password from my welcome email so that I can access my account. *(entry point)*
- **US-A4**: As a first-time user, I am blocked from all endpoints except change-password until I set a new password, so that temporary credentials cannot persist.
- **US-A5**: As a Member, I change my password and receive a new token without the must-change flag so that I gain full member access.
- **US-A6**: As the System, I auto-create a MEMBER account with a temporary password when a member is registered, and emit `AccountCreatedEvent` so that the welcome email delivers real working credentials.
- **US-A7**: As the System, I enable account login only while the linked member is ACTIVE, and disable it on INACTIVE/SUSPENDED/TERMINATED, so that login rights track membership standing.
- **US-A8**: As an Admin, I am the only role permitted to register members, list members, change status, and record dues payments, so that member data is protected.
- **US-A9**: As a Member, I access only my own profile and dues — via `/api/me*` or via `/api/members/{id}/**` where I am the owner — so that I cannot read or modify other members' data.
- **US-A10**: As a Member, I update only my phone and address via `PUT /api/me`, while membership number, email, DOB, join date, and status remain read-only.
- **US-A11**: As the System, I reject login for disabled accounts and return a generic 401 for bad credentials so that account state and existence are not leaked.
- **US-A12**: As an operator, I seed exactly one Admin from `.env` on startup if none exists, with a forced password change, so that the system is reachable without committing secrets.
- **US-A13**: As a developer, I keep `auth` internals package-protected and cross-module communication event-/facade-only so that `ApplicationModules.verify()` stays green.

## Implementation Build Order

1. **`auth` module skeleton** — `package-info.java` (`@ApplicationModule`), `Role`, `UserAccountEntity` + repository, `V4__init_user_account_table.sql`.
2. **Crypto/JWT** — `JwtService` (HS256, 8h, `Clock`), `JwtAuthenticationFilter`, Spring Security config (stateless, allow-list, default-deny). Add `spring-boot-starter-security` + a JWT library (e.g. `jjwt`) to `pom.xml`. Add `AUTH_JWT_SECRET`, `AUTH_JWT_TTL` to `.env`/`.env.example`.
3. **Account lifecycle** — `AccountCreatedEvent`; listeners for `MemberRegisteredEvent` (create + emit) and `MemberStatusChangedEvent` (enable/disable). Idempotent on email.
4. **Rewire notification** — welcome email listens to `AccountCreatedEvent`; drop the throwaway password generator.
5. **Auth REST** — `AuthController` (`/login`, `/change-password`), forced-change gate.
6. **Self-service + RBAC** — `MeController` (`/api/me`, `/api/me/dues`, `PUT /api/me`); apply method/URL security + owner-or-admin checks to existing member/dues routes.
7. **Seed admin** — startup seeder from `.env`, idempotent.
8. **Tests** — login/expiry/forbidden, forced-change gate, owner-vs-admin matrix, status→enabled sync, account-creation idempotency, `ModularityTest` + ArchUnit. (Requires Docker running for Testcontainers.)
